## Outcome
- **Verdict:** clean so far; memory holding (T+24h due ~03:45Z 11-27, T+2h20m check at 06:00Z)
- **What broke:** nothing in this deploy. The defect it fixes: memory grew with every new thread that read the database, up to threads × 32 MB.
- **Which gate should have caught it:** the image lane runs under the 400 MiB limit, but on a tiny database with no concurrency, so the caches never filled. No local lane had a production-sized database under load.
- **Gate change made as a result:**
  - `test_readers_are_pooled_with_a_small_cache_whatever_the_thread_count`, a test that the cache size and pool bound hold.
  - The image check now requires `/health` to report the 400 MiB limit, and `/health` reports thread and reader counts.
  - `test_startup_footprint` and `test_logging`.
  - A production-sized load benchmark is not yet a lane; it stays a scratch script.
