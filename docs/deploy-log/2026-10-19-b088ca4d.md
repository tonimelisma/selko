## Outcome
- **Verdict:** clean.
- **What broke:** nothing.
- **Which gate should have caught it:** none existed, and the gap was
  structural rather than an oversight. Two allowlists had to agree and nothing
  compared them — `20260728000001` had already patched the same class by adding
  the three types seen by then, which left the drift in place. Local tests
  could not catch it either: the frontend/unit suites never upload, and the
  integration suite had no case asserting the bucket would accept what the
  worker sends.
- **Gate change made as a result:**
  `backend/tests/integration/test_integration_attachment_mime_contract.py`
  reads the live bucket allowlist and the worker's own constants and asserts
  containment, including that each unbounded prefix has a matching wildcard —
  so a change to either side fails there instead of in production. Verified it
  can fail (above).
  `test_integration_revive_mime_dead_letters.py` executes the shipped revival
  `.sql` rather than a copy, because a `db reset` only proves a data migration
  parses against an empty table while the predicate is the whole migration.
  Also fixed two assertions in `dbb3c877`'s own tests that this run surfaced:
  one asserted `status == "ok"` (a whole-database claim that passed when
  written and failed once a neighbouring test left a dead letter behind), and
  one asserted a bare `status == "degraded"` which would pass even when
  something unrelated degraded the roll-up. The second now quiesces the other
  degrade sources inside its rolled-back transaction and asserts a threshold
  differential, so the result is attributable to the stall.
- **Other failures investigated in the same pass, no code fix warranted:**
  - The 34 terminally failed emails are historical. Last failure 2026-09-10;
    across 4.9h of post-restart load that drained 914 items and created 108
    events, `conflict_exhaustion_count` was 0 and the retry histogram
    `{1: 6, 2: 1}`. The conflict loop was fixed by the early-September fence
    work. They are terminal history, which is why `failed_emails` is
    deliberately unasserted. **Open question for the operator:** those 34
    emails may contain events the user never saw; reprocessing them is a data
    action, not a code change.
  - 3 `calendar_work_items` failed on 2026-08-22 (Google `HttpError 400`,
    `[Errno 11]`), so three events never reached the calendar. Requeueing is
    likewise a data action.
  - 57 `unsupported` attachments are email signature logos
    (`anthropic-wordmark.png`, `entrant-logo.png`). Legitimate terminal state,
    no health impact, no extraction value.
  - `main` CI is red on `Deploy to Staging` because the staging project is
    paused, which the operator has decided to leave as is. Tier 2 is therefore
    unavailable and this deploy had no post-merge staging tier.
