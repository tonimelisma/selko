## What was reverted

#376/#377/#378 built the consumer of that link: adopt a New-lane event when the
user's calendar already holds it. In production it drove
`commit_email_extraction` to **"Resolution conflicts exhausted" on every
attempt**, with no calendar mirror activity nearby, and took the email to a
terminal failure at attempt 3 of 3. Each attempt appears to invalidate the
fingerprint the next attempt is checked against, so the retry can never
converge.

Reverted in #379. The email was reprocessed on the reverted build and returned
`processed / event_matched` cleanly.

## Outcome
- **Verdict:** clean, after a rollback of the last three commits.
- **What broke:** the adoption path conflict-looped the resolution fence and
  burned one email's entire retry budget.
- **Which gate should have caught it:** none of them could, and that is the
  finding. The `prod` gate was green for all three of those deploys. The fence
  is a concurrency property between *repeated attempts against live data* — a
  mocked unit test has one attempt and a static candidate set, so it cannot
  observe a fingerprint that shifts between retries. This is the same
  "elapsed-time / production-data" axis §1a already names as the one local
  tests cannot reach.

  The concrete gap: **no gate exercises the retry path of a fenced commit.**
  Before the adoption rule is rebuilt, an integration test should commit the
  same extraction twice against real Postgres and assert the second attempt
  converges. A decision that writes hints and is then re-checked against a
  fingerprint covering those hints can never settle, and only a test that runs
  the loop twice can say so.
