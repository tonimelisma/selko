An email whose `text/plain` part is a placeholder no longer starves extraction.
Measured on the real production message, "You Got Tickets To Monster Jam"
carried a 14-byte plain part -- the single word "Ticketmaster" -- beside a
73,524-byte `text/html` part holding the whole confirmation. Selko stored the
stub, discarded the HTML, and handed the LLM 14 characters.

- `services/email_body.py` (new) renders an HTML part to text and picks
  whichever candidate says more. Relative rather than a length floor: no fixed
  minimum separates a placeholder from a genuinely terse email.
- `services/emails.py` uses that selection instead of trusting `text/plain`.
- `services/event_processing.py` replaces `body_text or snippet` with a
  substantiveness check; a stub is truthy, so the snippet fallback that existed
  for exactly this case never fired.
- `services/outlook.py` renders an HTML body rather than storing none. Graph
  normally honours `Prefer: outlook.body-content-type="text"`, which is why
  Outlook never reproduced the bug; this covers the case where it does not.

`href` targets are emitted as text deliberately: `body_text` also feeds
`build_hints()`, so a conversion that dropped link targets would have silently
disabled the join-URL matching built in #374/#375. On the real message the fix
recovers 27 URL tokens where the stub yielded none.

**Not an LLM defect.** The real extraction was run both ways before writing any
fix: given the recovered body the model returns Monster Jam,
2026-09-06 13:00-07:00, SAP Center at San Jose; given the 14-character stub it
returns nothing, which is correct for that input. No eval fixture was added,
because neither input is one the model gets wrong.

The operator clicked Reprocess and the event still did not appear, which is the
predicted behaviour and worth recording because it looks like the fix failing.
Measured on the live row: reprocess ran at 05:37:32Z on the deployed code,
`lock_generation` reached 7, and the outcome was `no_event` again. The
extraction-time guard worked correctly -- `is_substantive` rejected the 14-byte
stub and passed the 199-char snippet instead -- but that snippet is truncated
mid-word at "...Order # 73-17813/NCA Monster", before any date or venue, and
the LLM returned 0 events from it. Correct answer, insufficient input.

**Reprocess can never repair a row stored before this fix**, because it re-runs
extraction on stored data and never re-fetches from the provider. With
approval, one message was re-synced from Gmail via
`save_email_with_attachment_descriptors`, whose ON CONFLICT DO UPDATE is
restricted to content columns and does not touch `processing_status`,
`attempts`, `lock_generation` or `processed_at`. The prior row was recorded
first. `body_text` went 14 -> 8,551 chars and reprocessing produced the event.

The result is the interesting part. Extraction did not create a New-lane item:
it matched the entry already on the user's Google Calendar
(`p3m00lao3uv69jptmu9fvbslns`), wrote both an `origin=email` and an
`origin=google_calendar` source, applied a `material_update` proposal and
completed an `upsert` work item. That is the mirror-matching chain from
 #371-#375 behaving exactly as designed -- deduplicating against the real
calendar instead of queuing a duplicate for review. So "not in the review
queue" had two different causes before and after the repair, and only the first
was a defect.
