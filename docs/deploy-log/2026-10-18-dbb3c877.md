## Outcome
- **Verdict:** degraded — the deploy did what it shipped to do (stall ended,
  backlog drained, events resumed, zero 5xx), and exposed one pre-existing
  attachment defect that keeps the health check red.
- **What broke:** nothing from this change. One `text/markdown` attachment
  cannot be ingested and dead-letters instead of being classified
  `unsupported`.
- **Which gate should have caught the original stall:** none existed. Every
  health invariant measured either liveness (`tasks[].alive`, which was `true`
  the whole time because the loop *was* running — it had stopped asking) or
  queue *depth* (`items_pending`, which read 912 and degraded nothing). No
  signal measured whether claimable work was *moving*. That is the exact shape
  of the failures this directory already records: a green signal that meant
  less than it looked like.
- **Gate change made as a result:** `dbb3c877` / PR #383 —
  `items_stalled_seconds` on `health_work_state`, asserted in
  `assert-health.sh` under `ingestion` (not `work-state`, which must hold with
  workers off); `check-production-health.sh` now runs the `egress` surface it
  had never once run against production; and `/health/egress`'s `transport` is
  a bounded live probe instead of `pool is not None`, which was equally true
  of a wedged pool. Three further gate repairs found by needing the gate:
  `verify.sh --accept-stale-gmail-token` never worked (variable name
  mismatch), the working flag then tripped the skip budget on a run with zero
  failures, and the R5 `schema-compat` lane could not parse the Supabase CLI's
  output at all because a newer CLI appends an upgrade notice after the JSON —
  so its real finding was invisible under "cannot verify".
- **Follow-ups:** (1) the `text/markdown` attachment dead-letter above, which
  is what currently keeps `work-state` and `ingestion` red; (2) the staging
  project is paused, so Tier 2 is unavailable until it is restored — this
  deploy had no post-merge staging tier at all; (3) `conflict_exhaustion_count`
  15 with `fenced_writes_since_start` 1 and 34 terminally failed emails, all
  "Resolution conflicts exhausted", pre-existing and untouched.
